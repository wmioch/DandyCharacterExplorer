# Scheduled maintenance

The Dandy Character Explorer heartbeat runs every two days at 07:00 Australia/Sydney in its existing review chat. The separate video workflow and its upload approvals have their own schedule.

## Review changed evidence

Read the private maintenance ledger and source checkpoints. Inspect current task activity, Git status and the preview before writing. Keep one coordinating writer. Use isolated checkouts based on current origin/main and preserve unrelated edits.

For gameplay facts, check official release notes first and the current Dandy’s World Wiki for details the notes omit. Read the official Discord changelog only through an already running, connected Chrome session. Use public Roblox metadata and wiki revisions when the Discord notes are unavailable. Record what each changed revision establishes for the affected app records. Conflicts and missing values stay open until published evidence resolves them. Browser checks verify Explorer behavior. They do not substitute for game sources.

On the first wake of each Sydney month, assess whether there is a documented coverage gap. Audit affected records individually when there is a gap, and use a full inventory audit only for widespread discrepancies or loss of reliable coverage. Review major releases and new feedback as they arise. Preserve source revisions, unresolved evidence, and prior audit history privately.

Read only Dandy Character Explorer feedback from PollingStation. Retain IDs and sanitized request history, including non-actionable entries. Mark a feature request addressed after the entire request is resolved and live.

## Complete the preview release cycle

The shared local preview is a temporary review environment. Give each bundle an exact candidate commit in an isolated checkout. Run the [validation suite](testing.md) and have GPT-6.2 Astra Medium personally exercise the real controls and inspect desktop and narrow layouts in an isolated loopback browser. Keep feedback and analytics disabled.

- If Astra requests changes, fix them in the same run, validate the new commit, and request a fresh browser verdict. Repeat the cycle after each revision.
- When the browser review passes, use a separate GPT-6.2 Astra High reviewer for the exact release commit and dependencies where the delegated release policy requires it. A changes-required decision returns the bundle to implementation and fresh review.
- Publish approved bundles to the existing GitHub Pages path in the same run. Recheck origin/main and the exact approved commit immediately before pushing, then verify the exact CI and Pages results and read the live files. Bounded source-backed fixes follow the existing automatic path after validation.
- If a genuine evidence, device, tooling, product-scope, or publication blocker persists, preserve the bundle in a named local hold branch or isolated checkout. Record the exact commit, blocker and next evidence in the private ledger. Continue with independent candidates. Reopen held work when the blocker changes.

Finish each run with the shared preview at verified production and its feedback and analytics disabled. A passing browser check, a draft PR, or a request for changes is an intermediate step. Preserve blocked work off the shared preview. Keep unrelated branches and user edits intact.

Keep the workflow within the Explorer frontend. Cooldown statistics are deferred. The Azure backend, credentials, hosting, costs, network exposure and video publication are outside the maintenance scope.

Report what shipped, material new blockers and any genuine product decisions needed. Keep the exact tested app and harness commits, reviewer verdicts, push results, and live verification in the private ledger.
